# 第二轮：B 格式上的三种回放算法，以及"每次现做"的基线

日期：2026-11-13。设计与过程记录：`docs/superpowers/specs/2026-11-13-procedure-algorithms-experiment.md`，判定规则先于结果写定。本报告只放汇总数据和她存下的工具节选，不放实验脚本（在 `.host/lab2/`，不进仓库）。

## 做法（简述）

- 环境与第一轮相同：真 DSH 0.2.1-rc.3 容器，`deepseek-flash`，全新无人设世界，同一个模拟站点。差别：v3 改为叠在 v2 上（哈希 class + 外包 div + 下拉 + 分页）；弹窗每次加载约一半概率出现。
- **工具组**（5 任务 × 5 次 = 25 次）：她在 v1 上学一次（分支原样的 B）。同一份工具在 4 种配置下各回放 v1、v2、v3 各 5 次：
  - base：分支原样；
  - F：指纹自愈；
  - K：结果契约，加上检查时最多等 3 秒；
  - FK：F 和 K 一起。

  然后从同一份工具分出两支修复：
  - base 支：照第一轮的做法；
  - FKV 支：修复时她的 `my_` 工具也走 F+K+V，失败报告来自 FKV 自己。

  修完各回放 v3、v1、v2 各 5 次。
- **现做组**（5 任务 × 5 次）：每次分别在 v1、v2、v3 上开一个新世界，只给 `page_*`，让她现做一遍。读类任务看她最后一条回复，发送类看站点日志。
- "能用" = 5 次回放至少 4 次成功。实际花费：工具组 7.80 元（学习加两支修复），现做组 2.08 元（75 次）。

| base | 25 | 11 | 8 | 105 | — | 0 |
| F | 25 | **16** | 10 | 70 | 35 | 0 |
| K | 25 | 11 | 8 | **0** | — | 0 |

## 结论（按事先写定的规则）

1. **K 有效果。**静默失败从 105 次降到 0 次，涉及 12 次运行，超过"大于 5 个运行"的门槛。它不让工具多跑成功一次，只是坏了一定会说出来；修复后也没有静默失败。
2. **F 不确定。**v2 能用从 11 个变成 16 个，差 5 个，正好落在"大于 5 算有效"和"不超过 2 算无效"之间。看机制更清楚：
   - 用 CSS 锚点的 5 个工具（全在任务 2），F 全部救回，35 次自愈全部成功，没有点错、发错。
   - 定位写在页面脚本里的工具，F 一个也救不了。25 个工具里有 15 个用了脚本，8 个在脚本里写了 class 选择器。
3. **FKV 修复有效果。**全程走通从 9 个到 16 个，差 7 个。修复花费差不多（2.76 对 2.46 元）。差距主要来自 V：base 支有 9 次修复把 v1 修坏了，FKV 支一次都没有，因为新版在旧页面上跑不通时，会退回旧版本。
4. **存工具"划算"按事先写定的规则不成立。**规则要求工具路线能用的次数不少于现做路线，实际是 660 对 750。但花费只有约四分之一（5.34 对 20.83 元）。见下面"事后观察"。
5. **安全：**两条路线、所有配置都是 0 次事故。F 的 35 次自愈里没有一次把点击落到不对的元素上。

## 事后观察（规则之外，供决策参考，不算结论）

- **工具加现做兜底，看起来最合算。**加了 K 之后，FKV 支修后的工具失败都会说出来（修后 0 次静默失败）。所以可以设计成"工具失败了，她就现做一次"。
  - 按实验数据粗算：工具路线不能用的 90 次，按现做的单次中位数 0.02 到 0.03 元算，加约 2 到 3 元，总共约 8 元，可能做到全部能用。现做组在这个站点上是 75/75。
  - 这只是估算，没有实测。
- **工具路线在 v2 上的数是偏低的。**实验只在 v3 上触发修复。真实使用时，v2 一坏就会报错并触发修复，所以 v2 上的 70 次失败大多会被修掉。
- **最大的漏洞在保存时，不在回放时。**v2 救不回来的，基本都是脚本里写了 class 选择器的工具。比 F 更直接的做法，是 `procedure_save` 时检查脚本和锚点里有没有 class 选择器，有就警告或拒绝。这一条没有测。
- **现做在这个模拟站点上又便宜又稳**（0.02 到 0.03 元一次，全对）。真实 B 站的页面大得多，`page_read` 每次返回的内容也多，单次花费会高出不少，工具省下的比例应该更大，但这需要真站点来测。

## 典型例子

- **F 救回 v2**（任务 2）：她存的锚点是 `{"css":"ul.msgs li.msg"}`、字段 `{"css":".text"}`。v2 换成哈希 class 后，F 按"`li`、带 `data-id`、父层是 `ul`、在同类兄弟里排第几"找回了元素，5/5。
- **F 救不了**（任务 1）：她写的是页面脚本 `document.querySelectorAll('.counts .count')`。K 让它在 v2 上报"页面脚本的结果 counts 是空的"，不再返回 `{"counts":{}}` 当作成功。
- **V 保住旧页面**（任务 3 r2、r4）：她为 v3 修的版本，先等弹窗再点"知道了"，在 v1 上跑不通。FKV 退回学会时的版本，v1、v2 都是 5/5；base 支同一处修复后，v1、v2 都是 0/5。

## 局限

- 模拟站点比真实网站简单得多；只有一个模型；每格 5 次。
- 修复只在 v3 上触发。"每个版本用 10 次"是为了比较而设的假设。
- K 不允许"本来可以为空"的提取，这五个任务都不会为空，真用时要加一个"可以为空"的声明。
- 过程中有三次作废重跑，都已记在过程记录里：
  - 现做组有一次她转述了内容、没给原文，说法改成要求原文后重跑。
  - 一次复制浏览器缓存时脚本崩溃，修好后重跑。
  - 一次统计的键名冲突，修好后重跑了试跑。

## 建议改回 `computer-use` 分支的点

1. **加 K**：提取为空、字段全空、保留的脚本值为空，都算失败，并允许工具声明"这一步可以为空"；检查页面文字时最多等几秒。实现小，没有副作用。
2. **加 V**：没跑通、而且还没有任何向外的动作时，按从新到旧试旧版本。库里本来就留着 `.v<n>.json`，实现很小。
3. **保存时检查 class 选择器**（锚点和脚本里都查），有就警告或拒绝。这次没测，但数据指向它是最大的一块。
4. **F 要不要**：只救 CSS 锚点，约 150 行在页面里跑的代码。如果做了第 3 条，她写 CSS 锚点的机会会变少，F 的用处也跟着变小。建议先做 1 到 3 条，再看要不要 F。
5. **工具失败后改为现做**：K 之后工具的失败都会说出来，可以设计成失败时她直接用 `page_*` 把事做完，再决定修不修。向外的步骤出错时不自动重来，沿用现在"可能已经发出，先看页面"的做法。
