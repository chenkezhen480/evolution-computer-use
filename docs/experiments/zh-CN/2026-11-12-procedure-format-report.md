# 她自己存的工具用什么形式：A 纯 JSON / B JSON + 页面内脚本 / C 全脚本

日期：2026-11-12。设计见 `docs/superpowers/specs/2026-11-08-procedure-format-experiment.md`（判定规则在看结果前写定）。只含汇总数据和她存下的工具节选，不含实验脚本（在 `.host/lab/`，不进仓库）。

## 做法

- 被测代码：本地分支 `computer-use`（`5e7ef2b`）的 `computer/`。B 组原样；A 组拒绝 `script` 步骤；C 组把工具存成 `async (page, args) => …`，在 `node:vm` 里带 60 秒超时运行。三组的 `page_*` 原语、任务说明、模型完全相同。
- 环境：Docker 里的真 DSH（`runzhliu/deepseek-harness:0.2.1-rc.3-r1`），`deepseek-flash`，容器内 Chromium + Xvfb；全新世界、无人设、无记忆。
- 模拟站点三个版本：v1 语义化标记（她在这里学）；v2 class 换成哈希、每个元素外多包两层 div，文字不变；v3 在 v1 上加"更多"下拉（入口收进 `<template>`）、遮罩弹窗"新功能上线"、评论区分页。
- 五个任务：1 查三种未读数；2 读某人私信；3 给某人发私信（向外）；4 读全部评论含楼中楼（v3 要翻页）；5 回复某一楼（向外，v3 要翻页找楼）。
- 每次运行：v1 学并存工具 → 不调模型回放 v1×10、v2×10、v3×1 → v3 失败则把失败报告交给她修 → 回放 v3×10、v1×10（修完旧版还能不能用）。v3 第一次就过的，事后补回放 v3×10。
- 3 组 × 5 任务 × 5 次 = 75 次运行，全部完成；总花费 18.1 元。

"能用"指 10 次回放至少 9 次成功。

## 结论（按事先写定的规则）

1. **主指标三组打平**（9 / 8 / 9，波动远大于差距；加上"修完 v1 仍能用"也是 5 / 6 / 6）。
2. **第二指标（花费）A 明显更贵**：差距几乎全来自任务 4（翻页），A 每次 0.69–1.44 元，B 0.11–0.24 元、C 0.11–0.30 元，范围不重叠；A 在这个任务上 5 次只修好 2 次。B 与 C 的花费差（4.81 / 4.32）在波动范围内。
3. **B 与 C 打平时选更简单的 → B**，即保留 `computer-use` 分支现在的格式。三组都没有安全事故，这一条不起作用；但 C 的 `node:vm` 不是安全边界，真要上 C 还得另外做隔离，这也是选 B 的理由之一。

## 看到的现象

**纯 JSON 处理不了"不知道有几页"。** A 组修任务 4 时只能把每一页写死，而且每个 `extract` 覆盖上一次的结果，最后只返回了最后一页（修后 0/10 的那几次）：

```json
{"open":".../video/BV1lab"}, {"extract":{"list":{"css":"li[data-rpid]"}, …}},
{"open":".../video/BV1lab?page=2"}, {"extract":{…}},
{"open":".../video/BV1lab?page=3"}, {"extract":{…}}
→ 实际返回 {"rows":[{"author":"小李","content":"收藏了，慢慢看"}]}
```

**脚本让她第一次就写出能扛结构改版的工具。** C 组 v3 不修就能用的有 11 次（A、B 各 5 次）。任务 4 的典型写法：逐页打开直到没有"下一页"，按 `data-rpid` 和标签名而不是 class 取数据，所以 v2、v3 都不用修：

```js
for (let p = 1; p <= 100; p++) {
  await page.open(p === 1 ? base : base + '?page=' + p);
  const data = await page.eval("… document.querySelectorAll('li[data-rpid]') … return { rows, next };");
  …
  if (!data.next) break;
}
```

但 C 修得没 B 稳（12/14 对 20/20）：B 的修复通常只需要改一两个声明步骤，C 要改整段代码。

**改版后不修就坏，和形式无关。** 三组 v2 能用的都只有三四成，看过的失败工具原因都是她用 CSS class 定位（`.msgs`、`.counts .count`），哈希化后全部落空。这是锚点写法的问题，不是存储形式的问题。

**静默失败比报错多。** v2 上的失败大多不报错：提取到空，工具仍按 `summary` 模板返回"完成。"之类的话。真用起来她会以为"没有新消息"，这比报错危险。

**修好新版，旧版常常就坏了。** 三组都有一半左右。她修的时候只看得到 v3，就把"关弹窗、点'更多'"写死；B、C 写了条件也只覆盖了 v3 的两种情况，漏了 v1 的原样页面。B 站这类网站会灰度、会 A/B 测试，新旧页面同时存在是真实情况。

## 实验本身的局限

- v3 是在 v1 上改的，没有叠加 v2 的哈希 class，所以按 class 写的工具到 v3 反而能用。任务 2 的工具大多直接打开私信页地址，绕开了 v3 的"更多"下拉；弹窗只是遮住页面，不影响读文字，所以任务 2 的 v3 基本没考到东西。
- "全程走通"事先没把"修完 v1 仍能用"算进去；表里两种都列了，结论不变。
- 静默失败时交给她修的失败报告来自实验的判定器（"期望结果包含……"），真用时她只能看到工具返回了什么，修复率可能偏高。
- 偶数种子使 v3 的弹窗每次都出现，没有考"有时有、有时没有"的弹窗。
- 只有一个模型（deepseek-flash）、每格 5 次；并发 2–3 跑，页面时序可能比单独运行时更紧。
- 实验插件把工具挂在 headless 会话上，绕过了"只在家里会话"的接线；Chromium 以 `--no-sandbox` 运行（容器内）。

## 建议改回 `computer-use` 分支的点

收益最大的几条都和形式无关，三组都受益：

1. **锚点不用 class**：格式说明里明确"用角色 + 名称/文字、`data-*` 属性或标签结构，不用 class"；`procedure_save` 时对 `css` 锚点和脚本里的 class 选择器给出警告（或拒绝）。直接针对 v2 的六成失败。
2. **提取为空要报错**：`extract` 列表一条都没取到时按失败处理（或让工具声明"可以为空"）；`summary` 里没引用任何提取结果时保存时提醒。直接针对静默失败。
3. **向外动作后的 `check` 要等**：紧跟 `outward` 步骤的 `check` 像 `wait` 一样轮询几秒再判定。
4. **修复时提醒新旧都要能用**：修复说明加一句"改版可能是灰度的，旧页面也要能用；遇到可选的弹窗/下拉请写条件"，并在修复后用修复前的工具也能跑通的页面状态做一次核对（能做到的话）。
5. **给 JSON 一个累加**：`extract` 带 `as` 时多次提取能追加而不是覆盖——这一条只在不用脚本时才需要；选 B 的话用脚本即可，不必加。
