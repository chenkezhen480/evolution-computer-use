# 她的工具用什么形式：对比实验（设计）

日期：2026-11-08　代码基础：本地分支 `computer-use`（`5e7ef2b`）　状态：与用户确认方向，待写实施计划

## 要回答的问题

她把走通的步骤存成工具、坏了自己修——这件事用哪种形式最好：

| 组 | 形式 | 实现 |
|---|---|---|
| A | 纯声明式 JSON | `computer-use` 分支的格式，去掉 `script` 步骤 |
| B | 声明式 JSON + 页面内脚本 | `computer-use` 分支现状 |
| C | 全脚本 | 她写一个 `async (page, args) => …` 函数，只能用注入的 `page` 接口（open/read/click/type/press/wait/extract/eval，锚点和现有原语同一套），在隔离环境里带超时运行；向外发出的动作要写成 `page.click(锚点, { outward: true })` |

三组用同一套 `page_*` 原语、同一个模型、同一段任务说明，只有"怎么存成工具"那段说明和保存/回放的实现不同。

**判定规则（先写下，免得看了结果再改）：**主指标是"全程走通率"：一次运行里，她在 v1 学会并存下工具、这个工具在 v2 不修也能跑、到 v3 她又把它修好——三步都成功的运行占全部运行的比例。学习和修复花的 token 是第二指标。差距在重复间的波动范围内时，选更简单的那个（A < B < C），符合"少即是多"。安全事故（误点、重复发出）出现任何一次的组，除非能在格式层面堵住，否则不选。

## 模拟站点

一个本地 Node 服务，模仿"消息中心 + 私信 + 评论区"，带一个可登录的假账号，记录所有写操作（谁、什么时候、发了什么）供核对。三个版本：

- **v1**：她在这里学；之后回放 10 次看稳定性。
- **v2 外观改版**：class 名换成哈希、多包几层容器、文字不变——锚点按"角色 + 名称/文字"写的工具应该不受影响。
- **v3 结构改版**：入口挪进下拉菜单、出现随机弹窗、列表分页——需要她修。

## 任务

| # | 任务 | 考什么 |
|---|---|---|
| 1 | 查未读：私信几条、回复我几条、@我几条 | 提取、汇总、`onAlarm` 可用 |
| 2 | 读某人的私信（参数：对方名字） | 参数代入、列表提取、`messages` 归档声明 |
| 3 | 给某人发一条私信（参数：名字、内容） | 输入、向外发出、发送后确认 |
| 4 | 读一个评论区，含楼中楼 | 嵌套列表、翻页（v3 里需要循环） |
| 5 | 回复某一楼（参数：楼主名字、内容） | 定位到具体元素、向外发出、弹窗（v3 需要条件） |

任务 4、5 在 v3 里需要"有弹窗就关掉""翻到底"，这是给 C 组（脚本）的公平机会。

## 每次运行的流程

每个（组 × 任务 × 重复）：

1. **学**（v1，模型参与）：一轮对话交代任务和"做成后存成工具"。记录：是否完成、是否存了工具、对话轮数、输入/输出 token、工具调用次数、截图次数、用时。
2. **回放**（v1，不调模型）：实验脚本直接用插件的回放引擎跑她存的工具 10 次。记录成功次数、用时。
3. **改版存活**（v2，不调模型）：同样回放 10 次。
4. **修**（v3，模型参与）：先回放一次让它失败，把失败报告作为一条消息交给她："这个工具坏了，修好它。"记录：是否修好（修后的工具在 v3 回放 10 次的成功次数）、轮数、token。
5. **核对**：站点写日志里不该有的写操作（误发、重复发、发错人）算安全事故。

重复：每个组合 5 次。3 组 × 5 任务 × 5 次 = 75 次学习 + 75 次修复（模型），其余回放不花模型调用。

## 指标

- 学会率；学习 token / 轮数
- v1 回放成功率（稳定性）
- v2 不修存活率
- v3 修复成功率；修复 token / 轮数
- 失败报告的可诊断性：修复是否在 3 轮内完成
- 安全事故数
- 工具文件大小（她以后读、改的成本）

## 先试一次再全跑

先跑一个组合（B 组、任务 1、1 次）把整条流程走通，量出单次花费和用时，按此估出全量花费，告诉用户后再全跑。
